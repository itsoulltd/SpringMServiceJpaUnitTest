For **schema-based multi-tenancy with Spring Boot + Hibernate + Flyway + PostgreSQL**, the following is a widely used and maintainable approach.

---

# Step 1. Create only the tenant schemas

Your first migration should only create schemas.

**V1__create_schemas.sql**

```sql
CREATE SCHEMA IF NOT EXISTS tenant_a;
CREATE SCHEMA IF NOT EXISTS tenant_b;
```

Notice that we don't create any tables here.

---

# Step 2. Create tables only once

Create another migration.

**V2__create_tables.sql**

```sql
CREATE TABLE passenger
(
    id                  INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version             BIGINT,

    created_date        DATE,
    last_modified_date  DATE,

    created_by          VARCHAR(255),
    last_modified_by    VARCHAR(255),

    name                VARCHAR(255) NOT NULL,
    sex                 VARCHAR(20),
    age                 INTEGER,
    dob                 DATE,
    active              BOOLEAN
);

CREATE TABLE person
(
    person_id           BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    version             BIGINT,

    created_date        DATE,
    last_modified_date  DATE,

    created_by          VARCHAR(255),
    last_modified_by    VARCHAR(255),

    name                VARCHAR(255) NOT NULL,
    sex                 VARCHAR(20),
    age                 INTEGER,
    dob                 DATE,
    active              BOOLEAN
);
```

Notice there is **no schema name**.

---

# Step 3. Configure Flyway

```properties
spring.flyway.enabled=true

spring.flyway.default-schema=public

spring.flyway.schemas=public,tenant_a,tenant_b

spring.flyway.locations=classpath:db/migration
```

Flyway will execute every migration once for each configured schema.

The result is:

```
public
    passenger
    person

tenant_a
    passenger
    person

tenant_b
    passenger
    person
```

No duplicated SQL.

---

# Step 4. Disable Hibernate DDL generation

```properties
spring.jpa.hibernate.ddl-auto=validate
```

or

```properties
spring.jpa.hibernate.ddl-auto=none
```

Flyway becomes the single source of truth for schema management.

---

# Step 5. Add a new database change

Suppose you add

```java
private String email;
```

to `Passenger`.

Create

**V3__add_email.sql**

```sql
ALTER TABLE passenger
ADD COLUMN email VARCHAR(255);
```

No schema name.

Flyway executes it for

```
public
tenant_a
tenant_b
```

automatically.

---

# Step 6. A new tenant joins

Suppose a customer named "Acme" signs up.

Create a schema:

```sql
CREATE SCHEMA tenant_acme;
```

That's all that's needed at the database level.

---

# Step 7. Run Flyway for the new tenant

Instead of changing existing migration files, configure Flyway to target the new schema:

```properties
spring.flyway.schemas=tenant_acme

Or (not recommended)
spring.flyway.schemas=public,tenant_a,tenant_b,tenant_acme, .....<all-new-tenant>
```

or programmatically:

```java
Flyway.configure()
      .dataSource(dataSource)
      .schemas("tenant_acme")
      .load()
      .migrate();
```

Flyway executes:

```
V1
V2
V3
...
V20
```

inside `tenant_acme`.

Now it has exactly the same structure as every other tenant.

---

# Step 8. Next release

Suppose version 2 of your application introduces

```java
private String phoneNumber;
```

Create

```
V21__add_phone_number.sql
```

```sql
ALTER TABLE passenger
ADD COLUMN phone_number VARCHAR(20);
```

When Flyway runs:

```
public
tenant_a
tenant_b
tenant_acme
```

all receive the new column.

---

# Step 9. Flyway history

Each schema maintains its own migration history:

```
public.flyway_schema_history

tenant_a.flyway_schema_history

tenant_b.flyway_schema_history

tenant_acme.flyway_schema_history
```

Each history table tracks which migrations have been applied in that schema, allowing tenants to be provisioned or upgraded independently.

# Typical project structure

```
src
 └── main
     └── resources
         └── db
             └── migration
                 ├── V1__create_schemas.sql
                 ├── V2__create_tables.sql
                 ├── V3__create_indexes.sql
                 ├── V4__insert_default_data.sql
                 ├── V5__add_email.sql
                 └── V6__add_phone_number.sql
```

---

# Overall workflow

```text
                Deploy Application
                       │
                       ▼
               Flyway starts
                       │
                       ▼
      Reads db/migration/V1...Vn
                       │
                       ▼
      Executes pending migrations
      for each configured schema
                       │
                       ▼
      public   tenant_a   tenant_b
```

When a new tenant is onboarded:

```text
Customer registers
        │
        ▼
CREATE SCHEMA tenant_xyz
        │
        ▼
Run Flyway only for tenant_xyz
        │
        ▼
tenant_xyz now has all tables
and flyway_schema_history
```

This keeps a single, version-controlled set of migration files while allowing each tenant schema to evolve independently and consistently.
